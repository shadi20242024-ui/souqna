# مركز المساعدة والسياسات – سوقنا السويداء

**الإصدار:** 2026-11-19  
**المسار:** `assets/souqna-guide.js` و`assets/souqna-guide.css`  
**الفرع:** `feature/legal-help-2026-11-19` (مبني على `fix/admin-login-diagnostics-2026-11-18`)

## ما أُضيف إلى التطبيق
- نافذة قابلة للفتح من «حسابي» وحقول التسجيل، وصفحة «المساعدة والشروط» ضمن قائمة سطح المكتب.
- أربع علامات تبويب: طريقة الاستخدام، المواصفات والخدمات، شروط الاستخدام، وسياسة الخصوصية.
- واجهة عربية RTL متجاوبة مع الهاتف والكمبيوتر، بالألوان الزرقاء والذهبية المعتمدة.
- أسئلة شائعة تفرق بين الوظائف المتاحة والوظائف المستقبلية: الربط التلقائي بمنصات Facebook وInstagram، وقنوات الأسعار المحلية الإضافية.
- خانة موافقة صريحة عند إنشاء الحساب مع حفظ `acceptedTermsVersion` و`acceptedPrivacyVersion` و`acceptedAt` بطابع زمني من خادم Firestore.
- قاعدة تحقق ترفض إنشاء الحساب إذا غابت الموافقة أو اختلف الإصدار، وتمنع تعديل سجل الموافقة من المتصفح.
- نسخ ملفات الدليل إلى حزمة الاستضافة الآمنة وتخزين الموارد العامة فقط في PWA للاستخدام دون اتصال.

## تسلسل اختبار التسجيل
1. افتح «حسابي» ← «حساب جديد».
2. أدخل اسمًا وبريدًا تجريبيين وكلمة مرور.
3. افتح «قراءة الشروط» ثم «الخصوصية» وتأكد من بقاء الحقول دون تغيير.
4. جرّب الإرسال دون اختيار الموافقة: يجب أن تظهر رسالة تمنع إنشاء الحساب.
5. اختر خانة الموافقة وأكمل التسجيل في **محاكيات Firebase المحلية فقط**.
6. تحقق من وجود الحقول الثلاثة الجديدة في مستند المستخدم وتطابق تاريخ النسخة.

## متطلبات الاعتماد قبل الإطلاق التجاري
- الاسم القانوني الكامل للجهة المشغلة وعنوان/بلد المراسلة؛ واختبار عمل بريد الدعم المعلن واستقبال الشكاوى وطلبات الخصوصية، مع تحديد إجراء الاستجابة.
- مراجعة قانونية محلية لنطاق المسؤولية والبيانات والتحويلات، وعدم اعتبار النص الحالي مشورة قانونية نهائية.
- اعتماد شروط الاسترداد والإلغاء والخلافات ومدة الاحتفاظ بالسجلات والإجراءات المتعلقة بأصحاب الحسابات القُصّر.
- اختبار تحديث شروط الاستخدام مستقبلاً، مع آلية طلب قبول مجدد وتوثيق الإصدارات السابقة.
- التنسيق بين نشر **الواجهة وقواعد Firestore الجديدة معًا**. نشر الواجهة وحدها سيؤدي إلى رفض حفظ حقول الموافقة، بينما نشر القواعد وحدها قد يمنع التسجيل عبر نسخ الواجهة القديمة.
- فحص بيئة `souqna-staging` الحقيقية (Auth وFirestore والصلاحيات) قبل أي ترقية للإنتاج.
- لا تُجرِ أي نشر لقواعد Firestore أو وظائف Cloud Functions أو استضافة `souqna-sweida` دون موافقة صريحة.
- لا تَعِد بظهور الإعلان المدفوع على Facebook/Instagram قبل تفعيل الربط الرسمي واختباره.
- الأسعار العالمية استرشادية؛ الدولار الرسمي والموازي والفضة والنشرات المحلية المتقدمة لا تعتبر مزايا مفعّلة بعد.


## فحوصات جاهزية Staging (أضيفت في 19 نوفمبر 2026)

هذه المرحلة تُجهّز **بوابة تحقق للقراءة فقط**، ولا تنشر القواعد أو الاستضافة أو الدوال.

- `npm run check:staging:legal` يقرأ إصدار القواعد *المنشور بالفعل* من Firebase Rules API لمشروع `souqna-staging`، ثم يفحص اشتراط الموافقة على الإصدار الحالي وتاريخ الخادم. يتوقف عند عدم وجود صلاحيات Google Application Default Credentials أو اختلاف الإصدار؛ لا يحاول تعديل القواعد.
- `npm run check:staging:hosting` يتحقق من صفحتَي الاستضافة الافتراضيتين وهوية مشروع Staging ووجود مركز المساعدة وحقول الموافقة في HTML المنشور.
- `npm run check:staging:guide-assets` يفحص ملفات `souqna-guide.js` و`souqna-guide.css` الفعلية على كلا نطاقَي استضافة Staging، ويتوقف إذا كانت مفقودة أو معروضة كصفحة HTML بديلة أو تحمل إصدار شروط أقدم.
- `npm run check:staging:readiness` يفحص الاستضافة والدوال والنسخة القانونية وصلاحية المدير والأقسام وملفات دليل الاستخدام المنشورة. غياب أي شرط يعني **NOT VERIFIED**، وليس جاهزية للإطلاق.
- `scripts/preflight-staging.mjs` يتحقق من حزمة بناء Staging محلياً ومن تطابق إصدار وثائق التطبيق مع قواعد Firestore الموجودة في المستودع؛ هذا ليس إثباتًا لما نُشر في السحابة.
- `scripts/publish-staging-hosting.ps1` أصبح يمنع نشر Hosting فقط إذا لم تكن قواعد الموافقة المطبقة على Staging متوافقة مسبقاً؛ لا يرفع قواعد أو دوال تلقائياً.

### التسلسل الآمن عند اعتماد النشر
1. راجع نصوص الشروط وسياسة الخصوصية وأضف اسم الجهة القانونية ووسيلة الدعم الرسمية وسياسة الاسترداد.
2. افحص إصدار القواعد في المستودع وشغّل المحاكيات والاختبارات. لا ترفع ملفات أو بيانات اعتماد Firebase إلى GitHub.
3. اطلب إذناً منفصلاً لنشر **قواعد Firestore على `souqna-staging` فقط**. يجب مراجعة فترة التوافق مع الواجهات القديمة حتى لا تنقطع إمكانية تسجيل الحسابات أثناء الانتقال.
4. افحص قواعد Staging المنشورة باستخدام الأمر `check:staging:legal` بعد نشرها من قِبل مالك Firebase.
5. اطلب إذناً منفصلاً لنشر Hosting على Staging، ثم نفّذ فحوصات الاستضافة والتسجيل والتصفح والمتاجر والنجوم والدليل المحلي.
6. اترك مشروع `souqna-sweida` الإنتاجي وCloud Functions دون أي تعديل حتى اكتمال اختبار القبول والإذن المستقل.

**لم تُجرَ عملية نشر قواعد أو Hosting في هذه الإضافة.** ويتطلب الوصول إلى Firebase Staging الحقيقي صلاحيات ربط/قراءة منفصلة؛ نجاح اختبارات GitHub المحلية وحده لا يثبت جاهزية الموقع الفعلي.

## مسار إصدار Staging المحمي (بعد اعتماد النصوص)

تضم النسخة الآن ملف `scripts/publish-staging-legal-and-hosting.ps1` لإنجاز إصدار تجريبي كامل من جهاز Windows يملك حساب Firebase المخوّل؛ لا يمكن تشغيله عن بُعد من GitHub وحده دون هذه الصلاحيات.

يطلب هذا المسار تصريحاً صريحاً بمعرّف التجربة `souqna-staging` وإصدار الشروط `2026-11-19`، ويتحقق من فرع العمل ونظافته. قبل أي كتابة للسحابة يثبت الاعتمادات ويشغّل المحاكيات، ويتحقق من تطبيق Staging وإعدادات الواجهة، ومن خدمات التجربة والمدير والأقسام. ثم يحتفظ بنسخة محلية **للقواعد المنشورة سابقاً** داخل `artifacts/staging-rules-backups/` (مستثناة من Git)، وينشر **قواعد Firestore وحدها على Staging**، ويفحص إصدار الموافقة المنشور، وينشر Hosting على Staging بعد اجتياز البوابة، ويفحص الجاهزية النهائية.

من PowerShell في مجلد المستودع، بعد تنزيل آخر تحديث للفرع ومراجعة النصوص القانونية، ومع وجود حساب Google/Firebase المخوّل فقط:

~~~powershell
git switch feature/legal-help-2026-11-19
git pull --ff-only origin feature/legal-help-2026-11-19
$env:SOUQNA_ADMIN_EMAIL = "STAGING_ADMIN_EMAIL"
.\scripts\publish-staging-legal-and-hosting.ps1 -ConfirmProject souqna-staging -ApprovedLegalVersion 2026-11-19
~~~

**تنبيه:** هذا الأمر ينشر تغييرات حقيقية على *بيئة Staging فقط*. لا تنفذه قبل اعتماد النصوص وسياسة الاسترداد والجهة المشغلة؛ ولا تنفذه إذا كان Staging مستخدماً فعلياً من عملاء غير تجريبيين. توجد فترة انتقال قصيرة بين إصدار القواعد والواجهة قد يتعطل فيها إنشاء حساب عبر نسخة قديمة؛ يوصى بنافذة صيانة أثناء التجربة. إذا فشل نشر Hosting بعد نشر القواعد، لا يضعف السكربت القواعد تلقائياً، بل يوقف الإجراء مع تحذير واضح وتبقى النسخة الاحتياطية المحلية متاحة لمراجعة الاسترجاع. لا ينشر Cloud Functions ولا يغيّر `souqna-sweida`.

نشر القواعد وHosting معاً **لم يُنفّذ من المحادثة** لعدم توفر صلاحيات Firebase السحابية المطلوبة. نجاح CI لا يعني أن هذه الخطوات قد نُفذت على السحابة.

## ملاحظات هندسية
- `GUIDE_VERSION` في ملف الدليل وفي `firestore.rules` يجب أن يتطابق عند اعتماد نسخة جديدة.
- لا تُستخدم قواعد Firestore الجديدة لتخزين إثبات الدفع. تعتمد طلبات النجوم والتمييز على آلية المالية الحالية.
- لم يتم تعديل أي مفاتيح أو مشاريع Firebase في النسخة الإنتاجية، ولم تُنشر أي وظيفة.
