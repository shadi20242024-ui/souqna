# سوقنا SOUQNA — خطة نشر آمنة قابلة للتنفيذ

الحالة: **مستند تشغيل ومراجعة، وليس إذناً بالنشر.** تاريخ الإعداد: 16 تشرين الثاني 2026.

## الحدود المعتمدة

- التطبيق Web/PWA مخصص لسوق السويداء، عربي مع تصميم متجاوب باللون الكحلي/الأزرق والذهبي.
- المستودع: shadi20242024-ui/souqna. العمل في فرع feature/news-media-2026-11-16، طلب مراجعة رقم 2؛ لا يُدمج قبل فحص نهائي.
- النظام الحالي Firebase Authentication + Firestore + Firebase Hosting المقترح + Cloud Functions v2 للعمليات المالية.
- نظام النجوم: نجمة واحدة = 1 دولار بحسب سياسة المشروع. **لا توجد بوابة دفع آلية**؛ التحقق من وصول المال مسؤولية الإدارة، مع ضرورة تدوين مرجع إيصال التحويل.
- كل متجر من حساب المستخدم له باقة مستقلة، والإعلانات تظهر بعد مراجعة الإدارة.

## تحضيرات ضرورية قبل أي خطوة في المشروع الحقيقي

1. التحقق من الحساب الصحيح في Firebase ومن هوية مالك المشروع وتفعيل المصادقة متعددة العوامل للحسابات الإدارية إن أمكن.
2. اختيار مشروع Firebase تجريبي مستقل (staging). لا تستخدم بيانات العملاء الحقيقيين في الاختبارات، ولا تنسخ أرقام هواتفهم إلى بيئة الاختبار.
3. التأكد من أن موقع الإنتاج موجود بالفعل وأن رابط الاستضافة والدومين معروفان. **لم يتم التحقق من عنوان نشر حقيقي لسوقنا بعد.**
4. مراجعة قواعد Firestore الحالية والإصدار المنشور من الواجهة قبل تغيير أي شيء؛ لا نفترض أنها مطابقة لما في GitHub.
5. تحديد إجراء النسخ الاحتياطي لبيانات Firestore وسجل النجوم والطلبات، وتجربة الاسترجاع في مشروع اختبار. قد تتطلب خدمات النسخ/التصدير فوترة وصلاحيات خاصة.
6. مراجعة المستند المالي: كيف تؤكد الإدارة الدفع؟ من يسجّل إيصال التحويل، وما سياسة التراجع أو الاسترداد؟ يلزم سجل مراجعة منفصل.
7. Cloud Functions v2 تتطلب خطة Firebase Blaze وفوترة فعالة للنشر، مع رسوم محتملة بحسب الاستخدام. ضع حدود تشغيل وموازنة وتنبيهات قبل تفعيلها؛ **الاختبارات المحلية لا تستلزم نشر دوال مدفوعة**.
8. مراجعة الخصوصية، شروط الاستخدام، الصور غير القانونية، والإبلاغ والحذف، والشروط الخاصة بالأنشطة المدفوعة وفق البيئة القانونية المستهدفة.

## بناء النسخة المراجعة (محلياً فقط)

على جهاز يحتوي Node.js 22 وJava 21 وFirebase CLI:

~~~bash
npm install
npm --prefix functions install
npm test
npm run build:hosting
~~~

التحقق المطلوب: جميع اختبارات الصلاحيات وCloud Functions تنجح؛ اختبارات Chromium للكمبيوتر والهاتف تنجح؛ مجلد dist يحتوي فقط على index.html وsw.js وmanifest.webmanifest وlogo.png وأيقونات PWA وassets/responsive.css. **لا يحتوي على ملفات functions أو firestore.rules أو الشيفرة الاختبارية أو ملفات المشروع الخاصة.**

ملف firebase.json يحصر استضافة الويب في مجلد dist، لكنه لا ينفّذ النشر تلقائياً.

## اختبار البيئة المنفصلة قبل الدمج

- تجربة التسجيل، تسجيل الدخول، تسجيل الخروج، نشر إعلان مرفوض وآخر مقبول، وإنشاء أكثر من متجر لكل حساب.
- التحقق من أن حساب زائر غير مصادق لا يقرأ الإعلانات أو المتاجر المعلّقة.
- اختبار طلب النجوم بمبلغ مختلف عمّا يُرسل في النموذج والتأكد أن الخادم يعتمد المبلغ المسموح.
- فحص منع إعادة قبول الطلب نفسه، ومنع تصحيح النجوم مرتين بنفس operationId، وتسجيل كل خصم/إضافة في دفتر معاملات خادمي.
- اختبار طلبات البنر المدفوع، بحيث لا تنشر أي صورة أو إعلان قبل تحقق الإدارة من الدفع.
- اختبار شريط الأخبار في كل الصفحات، وصفحة الإعلانات والمتاجر والبحث العلوي ولوحة الإدارة على الكمبيوتر والهاتف.
- فحص ملفات PWA وعمل التحديث بعد تغيير Service Worker، والتأكد من عدم كشف البيانات الخاصة عند انقطاع الاتصال.
- اختبار الأداء الفعلي للصور وسلوك الحجم. **التخزين الحالي لبعض الصور داخل مستندات Firestore يحتاج نقلاً إلى خدمة تخزين كائنات قبل التوسع**.
- تفعيل App Check قدر الإمكان، وتحديد سياسة حذف الحساب والبيانات، والحدود ضد البريد المزعج، وقواعد Firestore على الإنتاج.

## تسلسل نشر مقترح — يحتاج موافقة صريحة ومراجعة المشروع الحقيقي

1. تحديد نافذة صيانة قصيرة وإيقاف الموافقات المالية اليدوية مؤقتاً.
2. أخذ نسخ من إعدادات وقواعد المشروع المنشور وقاعدة البيانات/دفتر النجوم واختبار إمكانية الرجوع.
3. نشر Cloud Functions **أولاً** على staging والتأكد من صلاحية مدير تجريبي. مثال بعد استبدال STAGING_ID وتأكيده:

~~~bash
firebase deploy --project STAGING_ID --only functions:souqnaFinance
~~~

4. نشر نسخة الويب من مجلد dist ثم قواعد Firestore الجديدة في staging، مع إعادة تحميل المتصفحات القديمة واختبار التوافق:

~~~bash
firebase deploy --project STAGING_ID --only hosting
firebase deploy --project STAGING_ID --only firestore:rules
~~~

5. اجتياز القائمة الكاملة على staging، ومراجعة آلية سجل الأموال والمصادقة، ثم إعداد قرار نشر منفصل للإنتاج.
6. عند موافقة المالك، إعادة التسلسل نفسه **ضمن نافذة صيانة** على مشروع الإنتاج المحدد يدوياً. بين نشر الواجهة والقواعد قد توجد فترة توافق مع جلسات قديمة؛ لا تفترض انعدام المخاطر.
7. إعادة فتح الموافقات المالية بعد قياس العمليات والسجلات والتأكد من عدم فقدان أي طلب أو إضافة رصيد مكررة.

## خطة الرجوع عند فشل النشر

- إيقاف اعتماد أي عملية نجوم أو دفع فوراً، والمحافظة على دفتر المعاملات دون مسحه.
- تحديد ما إذا كانت المشكلة في الواجهة أو الدوال أو القواعد أو البيانات، ومراجعة سجلات Cloud Functions/Firestore.
- استعادة نسخة واجهة مثبتة سابقة فقط بعد فحص توافقها مع **القواعد الأمنية الجديدة**؛ لا تُعد القواعد السابقة المتساهلة آمنة تلقائياً.
- لا تعيد تشغيل الدالة أو الطلب المالي تلقائياً إذا كان احتمال تنفيذ المعاملة قائماً؛ اعتمد على سجل العملية ومعرّف الطلب لتأكيد النتيجة.
- لا تدمج PR أو تنشر من CI تلقائياً. قرارات النشر والفوترة يجب أن تتم عبر الحساب الإداري المعتمد.

## عوائق الإطلاق الحالية

- مطابقة التصميم الأخير جزئية: شريط الكمبيوتر والبحث والأخبار والأقسام الجديدة أُضيفت، لكن قسم المفضلة وبعض الشاشات التفصيلية في المعاينة ما زالت بحاجة إلى تنفيذ وربط حقيقي.
- لا يوجد دليل على مراجعة قانونية محلية أو اختبار تحميل كبير أو تدقيق أمني مستقل.
- الدفعات ليست متصلة ببنك أو مزود دفع؛ يجب تطبيق سجل إثبات يدوي مضبوط.
- صور Firestore الحالية تحتاج خطة نقل إلى Storage، مع مراعاة صلاحيات الملفات والتكاليف.
- لا يوجد عنوان دومين/نشر إنتاجي مُتحقَّق منه هنا، ولا موافقة على تشغيل Blaze أو النشر الفعلي.

**قاعدة القرار: لا دمج، لا فوترة، ولا نشر قبل مراجعة جميع العوائق وتأكيد موافقة المالك على كل عملية مؤثرة.**
